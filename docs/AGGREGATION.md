# ICG 聚合技术说明

本文是对 ZTE TopFlow MU5252 B20 实机在 2026 年 8 月的观测与逆向结论，不是厂商协议
文档，也不包含服务器地址、设备身份、授权材料、配置抓取或厂商二进制。

## 它是什么

实体 Switch 上档进入 `SMULTIWAN` 后，设备启动厂商 ICG 客户端并按需取得运行配置。
客户端建立本地透明代理、`tun0` 和绑定到三路蜂窝链路的多条 TCP/UDP 外层隧道。业务
报文被封装后，调度器结合隧道可用性、有效 RTT、排队和限速条件选择发送路径；远端
服务器负责排序、重组、重传语义和统一出口。

实测单个持续 TCP 下载期间，三路物理链路能在同一秒同时接收数据，因此它不只是
`mwan3` 那种“一个连接选一张卡”的负载均衡。

## 它不是什么

- 不是蜂窝射频层的 Carrier Aggregation；三张 SIM 和三路基带仍相互独立；
- 不是 Linux MPTCP；设备当前内核和运行栈没有显示它使用标准 MPTCP；
- 不是普通 VPN；远端必须理解私有 ICG 会话、隧道标识、排序、重传和 NAT/代理语义；
- 不是固定均分；三路各有隧道不等于业务流量按相同比例发送。

## 与普通模式的区别

| 项目 | `MULTIWAN` | `SMULTIWAN` |
| --- | --- | --- |
| 主调度器 | `mwan3` | 厂商 ICG 客户端 + 远端服务器 |
| 单连接 | 固定到一条 WAN（除故障迁移） | 可将封装报文动态送往多条链路 |
| 虚拟接口 | 无 ICG `tun0` | 创建 ICG `tun0` |
| 远端依赖 | 普通互联网出口 | 必须有兼容 ICG 服务端 |
| `12:1:1` 权重 | 当前普通模式策略 | 与 ICG 无关 |

## 能否自建服务端

客户端运行配置可以描述服务器、端口、TUN 和会话信息，说明目标地址不是完全硬编码。
但“地址可改”不等于“任意 VPS 可用”。自建端至少需要实现私有握手、认证、隧道状态、
序号/校验、TCP 透明代理、UDP NAT、重排、重传与统一出口。

目前没有找到可直接部署的公开官方服务端、完整协议文档或兼容开源实现。因此：

- 厂商服务器是当前原厂 ICG 最现实、唯一已验证的后端；
- 自建在理论上不是绝对不可能，但实际等同于重新实现私有协议，尚无可用方案；
- 如果目标是开放协议的三路聚合，应把 MPTCP/OpenMPTCProuter、Glorytun 等视为新的
  数据面项目，而不是把它们称为 ICG 服务端替代品。

## 可观测性边界

判断聚合在线应组合检查模式、客户端进程、`tun0`、三路外层连接、握手状态和真实接口
流量。只看配置、只看 `tun0` 计数，或者只看到三张卡注册成功，都不能单独证明业务在
聚合。

短时吞吐会受到蜂窝调度、信号、测试服务器、ICG 冷启动、拥塞控制和远端负载影响。
公开文档保留机制结论，不把某一次速率当成长期性能承诺。
